# 1 — What is agentic development?

## 1.1 The concept in one sentence

Agentic development means **programming with an AI assistant that does more
than complete code**: it understands your project, enforces quality rules,
orchestrates verifications, and can even coordinate multiple specialists
to solve a problem.

## 1.2 The difference from classic autocomplete

| | Classic autocomplete | Agentic development |
|---|---|---|
| **Scope** | Completes the current line | Understands the project architecture |
| **Context** | The open file | The entire codebase + rules |
| **Initiative** | Waits for your input | Proactively suggests, verifies, fixes |
| **Quality** | No verification | Enforces security and quality rules |
| **Collaboration** | Single model | Multiple specialized "agents" |

## 1.3 Key concepts

### Skills

A **skill** is a set of specialized instructions the agent can invoke. For example:

- `python-patterns`: knows Python idioms, PEP 8, type hints
- `security-review`: can audit the security of an API endpoint
- `tdd-workflow`: applies the test-first cycle (write the test, then the code)
- `laravel-patterns`: knows Laravel/Symfony/PHP conventions

Your `.agents/skills/` folder contains more than 230 of them. The agent consults
them **automatically** based on the context of your question.

### Workflows (commands)

A **workflow** is a step-by-step procedure you trigger explicitly.
They live in `.agents/workflows/`. Examples:

- `/code-review`: launches a structured code review
- `/plan`: creates an implementation plan before coding
- `/build-fix`: detects and fixes build errors
- `/test-coverage`: analyzes test coverage

### Rules

The **rules** in `.agents/rules/` are permanent guardrails:

- `gateguard.md`: forces the agent to verify facts before writing code
- `bash-safety.md`: prevents dangerous commands (`rm -rf /`)
- `config-protection.md`: protects sensitive files (`.env`, SSH keys)
- `quality-gate.md`: verifies quality after each change

These rules apply **permanently**, without you having to think about them.

### Hooks (lifecycle events)

The **hooks** in `.agents/rules/hooks/` trigger at specific moments:

```
bash-safety         → checks security of Bash commands
config-protection   → protects sensitive configuration files
design-quality      → frontend quality check before display
gateguard           → forces fact-finding before any change
quality-gate        → quality check after a file is modified
session-context     → loads project context at startup
strategic-compaction → optimizes the context window during a session
```

### Dependency graph

The `skill-graph.json` file maps relationships between skills:

- **`depends_on`**: skill A requires skill B
- **`enhances`**: skill A improves skill B
- **`related_to`**: skills are thematically linked

The agent uses this graph to automatically load the relevant skills.

### Agent identity (`system.md`)

The `system.md` file is the agent's **brain**. It contains:

- Its identity and role
- The complete catalog of available skills
- Active security rules
- Active hooks

It is the first thing the agent reads at the start of each session.

## 1.4 Why is this useful for a junior developer?

1. **Safety net**: the rules prevent classic mistakes
   (deleting a production file, committing a password, etc.)
2. **Skill building**: the skills contain best practices
   for each technology — the agent applies them in real time
3. **Permanent code review**: instead of waiting for a senior review,
   the agent checks quality immediately
4. **Time savings**: workflows automate repetitive tasks
   (project setup, tests, deployment)

# 2 — Setting up the agentic framework in Antigravity

## 2.1 Prerequisites

Before starting, make sure you have:

- [ ] **Google Antigravity** installed and working
- [ ] **The `.agents/` folder** at the root of your project (generated by the
      `everything-antigravity.sh` script)
- [ ] `python3` installed (for maintenance tools)

## 2.2 Verify the installation

Open a terminal in your project and run:

```bash
# Check that the .agents/ folder exists
ls .agents/

# Expected output:
# ea-install-state.json  rules/  scripts/
# security-report.json   skill-graph.json  skills/  system.md  workflows/
```

If the folder does not exist, run the installation:

```bash
bash everything-antigravity.sh ./everything-claude-code
```

## 2.3 Understanding the structure

```
your-project/
├── .agents/                        ← The agentic framework
│   ├── system.md                  ← Agent identity (do not modify)
│   ├── skills/                    ← 234 specialized capabilities
│   ├── workflows/                 ← 68 invocable procedures
│   ├── rules/                     ← 87 permanent rules
│   │   └── hooks/                 ← 7 automatic triggers
│   ├── scripts/                   ← 5 maintenance tools
│   ├── skill-graph.json           ← Map of skill relationships
│   └── security-report.json       ← Latest security audit
├── src/                           ← Your application code
├── tests/                         ← Your tests
└── ...
```

> **Golden rule**: never manually modify files in `.agents/`.
> Use the `everything-antigravity.sh` script for updates.

## 2.4 Opening the project in Antigravity

1. Launch Google Antigravity
2. Open your project folder (`File → Open Folder`)
3. The agent automatically detects the `.agents/` folder and loads:
   - The identity from `system.md`
   - Relevant skills from `skills/`
   - Rules from `rules/`

## 2.5 Interacting with the agent

### Asking a question

Open the agent chat panel and ask your question in natural language:

```
How do I create a Symfony controller to display a list of articles?
```

The agent will:
1. Detect that you are working with Symfony (via the `laravel-patterns` skill
   and your project files)
2. Consult the quality rules (`quality-gate.md`)
3. Propose code compliant with Symfony conventions
4. Verify security (no SQL injection, no XSS)

### Using a workflow

Type a slash command in the chat:

```
/plan Create an RSS import system with parsing and database storage
```

The agent will:
1. Analyze your existing codebase
2. Identify patterns and conventions already in place
3. Produce a detailed implementation plan
4. **Wait for your approval** before touching any code

### Letting the rules act

You don't need to do anything — the rules apply automatically:

- If you ask to run `rm -rf /`, the `bash-safety` hook blocks it
- If the agent wants to modify `.env`, `config-protection` asks for confirmation
- After each file modification, `quality-gate` verifies the result

## 2.6 Maintenance tools

Five utility scripts are available in `.agents/scripts/`:

```bash
# Full installation diagnostic
.agents/scripts/ea-doctor

# List all installed skills
.agents/scripts/ea-list skills

# View the dashboard
.agents/scripts/ea-status

# Clean uninstall
.agents/scripts/ea-uninstall
```

## 2.7 Updating the framework

When a new version of EA is available:

```bash
cd everything-claude-code && git pull && cd ..
bash everything-antigravity.sh ./everything-claude-code --project ./your-project
```

The reinstall is **idempotent**: only modified files are updated.
The `--project` flag ensures the update targets the correct `.agents/`.

## 2.8 — Observing agent behavior through logs

The agentic framework includes a **logging** mechanism that traces calls to
skills, workflows, rules, and hooks.

This is an essential learning tool: it lets you see what the agent
does "under the hood".

### The 2 log levels

| Level | Behavior | Recommended use |
|---|---|---|
| `silent` | No trace | Production, normal work |
| `info` | One line per call (time, type, resource) | Training, exploration |

### Changing the log level

```bash
.agents/scripts/ea-logger level info     # enable logging
.agents/scripts/ea-logger level silent   # disable
.agents/scripts/ea-logger level          # view current level
```

### Reading logs in real time

Open a second terminal in your project and run:

```bash
.agents/scripts/ea-logger tail
```

Each call to a resource will appear in real time as you interact
with the agent in Antigravity.

### Consulting logs after the fact

```bash
.agents/scripts/ea-logger view 50    # last 50 entries
.agents/scripts/ea-logger stats      # today's statistics
.agents/scripts/ea-logger clear      # archive and clear
```

### Reading a log line

```
14:32:07 | SKILL    | python-patterns
14:32:19 | WORKFLOW | /plan
14:33:01 | HOOK     | quality-gate
──────── | ──────── | ─────────────
Time       Type       Resource
```

| Field | Meaning |
|---|---|
| `HH:MM:SS` | Exact time of the call |
| `TYPE` | `SKILL`, `WORKFLOW`, `RULE`, `HOOK` |
| Resource name | The invoked resource (`python-patterns`, `/plan`, etc.) |

> **Tip**: the actual elapsed time between two calls can be calculated
> from the timestamp difference between two consecutive lines.

### Where are log files stored?

```
.agents/
└── logs/                          ← created automatically on first call
    ├── agent-2026-05-09.log       ← today's log (one file per date)
    └── agent-2026-05-08.log       ← previous days' logs
```

> **Note for juniors**: these logs trace what the agent *declares* it is doing.
> This is a training tool, not a production audit. For exact telemetry
> (tokens, costs), consult the Antigravity dashboard.

## 2.9 — Calibrating the agent with a session-start prompt

In practice, the agent can "forget" to call the logger or call it with
generic values (`response antigravity`) instead of the real resource names.
To avoid this, **paste this prompt at the start of each work session**:

### Calibration prompt (copy-paste)

```
Before starting, read and strictly apply the rule `.agents/rules/agent-logging.md`.

Reminder: on EVERY response, your FIRST action must be to execute:
.agents/scripts/ea-logger log <type> <name> || true

Rules:
- <type> = skill | workflow | rule | hook (NEVER "response")
- <name> = actual resource identifier (NEVER "antigravity" or "unknown")
- If I invoke /plan → ea-logger log workflow /plan
- If you apply jpa-patterns → ea-logger log skill jpa-patterns
- If no specific skill/workflow → ea-logger log rule <rule-name>
- If multiple resources in one response → one call per resource

Confirm you have understood by executing:
.agents/scripts/ea-logger log rule agent-logging || true
```

### Why this works

This prompt leverages three complementary mechanisms:

1. **Reference to the rule file** — the agent reads it and integrates the
   full instructions, including examples and the decision table
2. **Concrete ✅/❌ examples** — reduces ambiguity for any model
3. **Verification action** — the agent must *prove* its understanding by
   executing the command, which immediately validates that the script works

### Automatic guardrails

Even without this prompt, the `ea-logger` script automatically rejects invalid
calls through two validations:

- **Invalid type** → `⚠️ ea-logger: invalid type 'response'. Must be one of:
  skill workflow rule hook`
- **Generic name** → `⚠️ ea-logger: invalid name 'antigravity'. Use the actual
  resource identifier.`

These validations are defined in `.agents/scripts/ea-logger` (function
`cmd_log`). If the call fails, the `|| true` prevents blocking the agent's
response — but the error is visible in the terminal.

### Verifying the logger works

After pasting the calibration prompt, check in a second terminal:

```bash
.agents/scripts/ea-logger tail
```

You should see the first line appear:

```
HH:MM:SS | RULE | agent-logging
```

If it appears, the agent is correctly calibrated for the session.

# 3 — Step-by-step example: Symfony AI digest application

We will build a complete web application that:

- Collects RSS feeds from reference AI websites
- Parses and stores articles in a database
- Displays a daily digest of AI news
- Provides an intelligent summary of each article

## Step 0 — Create the project

### 0.1 Initialize the Symfony project

Open Antigravity and ask the agent:

```
Create a new Symfony 7 project with the Webapp pack. The project is called
"ai-press-review". Use PHP 8.3, PostgreSQL, and Twig for the frontend.
```

The agent will run:

```bash
composer create-project symfony/skeleton ai-press-review
cd ai-press-review
composer require webapp
composer require doctrine/orm doctrine/doctrine-bundle
```

### 0.2 Install the agentic framework


The `--project` flag does two things simultaneously:
1. **Automatically detects PHP/Symfony** and activates relevant skills:
   `laravel-patterns`, `php-patterns`, `database-migrations`, `security-review`, `tdd-workflow`
2. **Installs `.agents/` directly into `./ai-press-review/`** — no need to `cd` into the project

### 0.3 Open in Antigravity

```
File → Open Folder → ai-press-review/
```

The agent automatically loads the `.agents/` framework and now knows your stack.

## Step 1 — Model the data

### 1.1 Request a plan

In the Antigravity chat:

```
/plan Create the data model for an AI news digest application. I need:
- RssSource (name, feed URL, category, active/inactive)
- Article (title, link, content, publication date, collection date)
- Summary (summary text, keywords, relevance score)
Each source has multiple articles, each article has one summary.
```

The agent produces a detailed plan. **Read it and validate** before continuing.

### 1.2 Generate the entities

```
Generate the Doctrine entities for the validated data model.
Use PHP 8 attributes (#[ORM\Entity]), not annotations.
Add Symfony validations (#[Assert\NotBlank], etc.).
```

The agent generates three files:

**`src/Entity/Source.php`**:

```php
#[ORM\Entity(repositoryClass: SourceRepository::class)]
class Source
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 255)]
    #[Assert\NotBlank]
    private string $name;

    #[ORM\Column(length: 500)]
    #[Assert\Url]
    private string $url;

    #[ORM\Column(length: 100)]
    private string $category = 'general';

    #[ORM\Column]
    private bool $active = true;

    #[ORM\OneToMany(targetEntity: Article::class, mappedBy: 'source')]
    private Collection $articles;
}
```

**`src/Entity/Article.php`**:

```php
#[ORM\Entity(repositoryClass: ArticleRepository::class)]
class Article
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 255)]
    #[Assert\NotBlank]
    private ?string $title = null;

    #[ORM\Column(type: Types::TEXT, unique: true)]
    #[Assert\Url]
    private ?string $link = null;

    #[ORM\Column(type: Types::TEXT, nullable: true)]
    private ?string $content = null;

    #[ORM\Column(nullable: true)]
    private ?\DateTimeImmutable $publishedAt = null;

    #[ORM\Column]
    private ?\DateTimeImmutable $collectedAt = null;

    #[ORM\ManyToOne(inversedBy: 'articles')]
    #[ORM\JoinColumn(nullable: false)]
    private ?Source $source = null;

    #[ORM\OneToOne(mappedBy: 'article', cascade: ['persist', 'remove'])]
    private ?Summary $summary = null;
}
```

**`src/Entity/Summary.php`**:

```php
#[ORM\Entity(repositoryClass: SummaryRepository::class)]
class Summary
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private ?int $id = null;

    #[ORM\Column(type: Types::TEXT)]
    private string $text;

    #[ORM\Column(type: Types::JSON)]
    private array $keywords = [];

    #[ORM\Column(type: Types::FLOAT)]
    private float $relevanceScore = 0.0;

    #[ORM\OneToOne(inversedBy: 'summary')]
    #[ORM\JoinColumn(nullable: false)]
    private Article $article;
}
```

### 1.3 Generate the migration

```
Generate the Doctrine migration for these entities.
```

```bash

```

> **Note**: the `quality-gate` hook automatically verifies that the entities

## Step 2 — Create the RSS collection service

### 2.1 Request the implementation

```
Create a RssCollector service that:
1. Reads all active RSS sources from the database
2. For each source, parses the RSS feed with SimplePie or FeedIo
3. For each article not yet in the database (check by URL),
   creates an Article entity and persists it
4. Returns the number of imported articles

Use Symfony dependency injection.
Add a console command `app:rss:collect` to trigger the collection.
```

The agent generates:

**`src/Service/RssCollector.php`** — the collection service:

```php
class RssCollector
{
    public function __construct(
        private readonly SourceRepository $sourceRepo,
        private readonly ArticleRepository $articleRepo,
        private readonly EntityManagerInterface $em,
        private readonly LoggerInterface $logger,
        private readonly ValidatorInterface $validator,
    ) {}

    public function collect(): int
    {
        $imported = 0;
        $sources = $this->sourceRepo->findBy(['active' => true]);

        foreach ($sources as $source) {
            // RSS parsing, URL-based deduplication, validation, persistence
        }

        $this->em->flush();
        return $imported;
    }
}
```

**`src/Command/RssCollectCommand.php`** — the console command:

```php
#[AsCommand(name: 'app:rss:collect', description: 'Collect articles from RSS feeds')]
class RssCollectCommand extends Command
{
    public function __construct(private readonly RssCollector $collector)
    {
        parent::__construct();
    }

    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        $io = new SymfonyStyle($input, $output);
        $count = $this->collector->collect();
        $io->success(sprintf('%d article(s) successfully imported!', $count));
        return Command::SUCCESS;
    }
}
```

## Step 5 — Automate the collection

### 5.1 Install dependencies

Two components are required:

```bash
composer require symfony/scheduler
composer require dragonmantank/cron-expression
```

> **Note**: `dragonmantank/cron-expression` is required by Symfony Scheduler
> whenever `RecurringMessage::cron(...)` is used. Without it, Symfony will
> throw an exception at runtime.

### 5.2 Configure the schedule

```
Configure the Symfony Scheduler to run the RSS collection every hour
and the AI digest 10 minutes after. Use the symfony/scheduler component
with cron expressions.
```

The agent generates the `DefaultScheduleProvider` with two precise tasks:

```php
#[AsSchedule('default')]
class DefaultScheduleProvider implements ScheduleProviderInterface
{
    public function getSchedule(): Schedule
    {
        return (new Schedule())
            ->add(
                RecurringMessage::cron('0 * * * *', new RssCollectMessage()),        // at h:00
                RecurringMessage::cron('10 * * * *', new ArticlesSummarizeMessage()) // at h:10
            );
    }
}
```

### 5.3 Verify

```bash
php bin/console debug:scheduler
# Should display both tasks with their next execution time
```

### 5.4 Start the background worker

```bash
php bin/console messenger:consume scheduler_default
```

This process must remain active (in production, use Supervisor or a
systemd service) for scheduled tasks to execute automatically.

## Tips for getting the most out of agentic development

### ✅ Do

- **Be precise** in your requests: "Create a controller with dependency
  injection and CSRF validation" rather than "Make a controller"
- **Use `/plan` before coding**: the agent analyzes your codebase and
  proposes a consistent approach
- **Read plans before approving**: the agent waits for your agreement
- **Ask for tests**: the `/test-coverage` workflow is your best friend
- **Do regular reviews**: `/code-review` after each feature

### ❌ Don't

- **Don't modify `.agents/`** manually — use the install script
- **Don't disable the rules** — they are there to protect you
- **Don't do everything in one request** — break it into steps
- **Don't blindly approve** — read and understand the generated code
- **Don't skip tests** — they will save your life

### 💡 Advanced tips

1. **Combine workflows**: `/plan` then `/code-review` then `/test-coverage`
2. **Use `ea-list`** to discover skills you don't know about
3. **The `--verbose` mode** of the install script shows you exactly
   which skills are activated for your stack
4. **Consult `skill-graph.json`** to understand skill relationships

### 2.1 Generate JPA entities

```
- Hexagonal architecture: entities in the domain package
- Modern JPA annotations (no XML)
- Bean Validation (@NotBlank, @Size, etc.)
- Bidirectional Document ↔ Category relationships (ManyToOne)
- Automatic auditing (createdAt, updatedAt via @EntityListeners)
- Indexes on category_id and title for searches
```

> **Skills used**: `jpa-patterns`, `java-coding-standards`,
> `hexagonal-architecture`, `coding-standards`
> **Rule**: `java-coding-style` — the agent automatically applies Java conventions

**`src/main/java/com/example/vault/domain/Document.java`**:

```java
@Entity
@Table(name = "documents", indexes = {
    @Index(name = "idx_doc_category", columnList = "category_id"),
    @Index(name = "idx_doc_title", columnList = "title")
})
@EntityListeners(AuditingEntityListener.class)
public class Document {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @NotBlank
    @Size(max = 255)
    @Column(nullable = false)
    private String title;

    @NotBlank
    @Column(columnDefinition = "TEXT", nullable = false)
    private String content;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "category_id", nullable = false)
    private Category category;

    @CreatedDate
    @Column(nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(nullable = false)
    private LocalDateTime updatedAt;

    // constructors, getters, setters...
}
```

## Step 4 — Web import service via curl.md

### 4.1 Design the import service

```
Design and implement the WebImportService that:

1. Receives a URL, title, and category from the user
2. Calls the curl.md API to convert the web page to Markdown:
   - Endpoint: https://curl.md/api/convert
   - Method: POST { "url": "https://example.com/article" }
   - Response: { "markdown": "# Converted content..." }
3. Creates a Document with the received Markdown, chosen title, and category
4. Handles errors: invalid URL, service unavailable, timeout (5s)

Use RestClient (Spring 6.1+) for the HTTP call.
Hexagonal architecture: WebConverter port in domain/, RestClient adapter in infra/.
```

> **Skills**: `springboot-patterns`, `hexagonal-architecture`, `api-design`
> **Rule**: `security-baseline` — URL validation, no SSRF

### 4.2 Secure the import

```
Audit the security of WebImportService:
- URL validation (https scheme only, no localhost/private IPs)
- Limit imported content size (1 MB max)
- Rate limiting (5 imports per minute per user)
- Sanitization of received Markdown (XSS in links/images)
- Timeout and circuit breaker on curl.md call
```

If the build fails after security fixes:

```
/build-fix
```

> **Skill**: `springboot-security` — Spring security patterns
> **Skill**: `security-review` — systematic audit
> **Rule**: `common-security` — verifies no API key is hardcoded
> **Workflow**: `/build-fix`

### 4.3 Import integration tests

```
4. Security test (localhost URL → rejected with 400)
5. Timeout test (response > 5s → clean fallback)

Use Testcontainers for PostgreSQL and WireMock for curl.md.
```
